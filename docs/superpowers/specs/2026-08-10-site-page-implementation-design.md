## 1. Scope

Build one new page, `site.html`, that presents the Site entity page from the widget catalog as **three cumulative tabs** — Stage A, Stage A+B, Stage A+B+C — so the build sequence itself is visible and can drive a sequencing conversation with engineering. This is a single implementation covering all three catalog stages at once (not three separate build rounds); the "staging" is a UI/navigation device, not a phased delivery plan.

Widgets show current values plus inline trend sparklines where the metric is gauge-like (latency, loss, throughput, client count). No click-to-expand trend overlays (the modal/detail-chart pattern used on the other 3 pages) — that's deferred to a later round once this page's shape is validated.

## 2. Page & Navigation

- New page `site.html`, alongside `index.html`, `sdwan.html`, `switch.html`, `access-point.html`.
- `NavigationManager._pages` gets a new entry: `{ key: 'site', label: 'Sites', href: 'site.html', icon: 'fa-building' }`.
- Header right-side selector gets a third branch (today it's `isSummary ? scopeSelector : deviceSelector`): a **site selector** dropdown, grouped by region like the existing device selector is grouped by site. Selecting a site re-renders the page for that site; the choice is reflected in the URL (`?site=NYC-HQ`) the same way device pages do it with `?device=`.
- Below the header: a persistent **site identity card** (name, region, device counts by type, WAN circuit count/types) — unaffected by tab selection, mirroring the device-info card pattern on the other 3 pages.
- Below the identity card: 3 tabs — **Stage A**, **Stage A+B**, **Stage A+B+C** — using the same `data-tab` / `SharedUI.switchTab` mechanism as the Overview/Diagnostics tabs on `switch.html`/`sdwan.html`/`access-point.html`. Each tab's content is additive: Stage A+B contains every Stage-A widget plus B's; Stage A+B+C contains everything.

## 3. Data Plan

### 3.1 Reused as-is (no new data)

| Widget need | Source |
|---|---|
| Device counts by type, switch/AP health rollup, device inventory table | `devices.json` + `network-data.json` `deviceStatus` (existing `status` enum: online/warning/critical/offline) via `DataLoader.getDevicesBySite` |
| Site-scoped alert feed | `alerts.json` via `DataLoader.getAlertsBySite` |
| Active wireless client count (current value) | `DataLoader.getClientCountByType('accessPoints', site)` |
| Time-to-Connect breakdown | `DataLoader.getFrustrationData(site)` — already site-scoped, already synthesizes a breakdown when a device lacks one |
| Cellular status/signal per gateway | `DataLoader.getDeviceData(gatewayId, 'gateway')` merge of `gateway-defaults.json` + `device-overrides.json` (already has `cellular.status`/`signalStrength`) |

### 3.2 New file: `data/site-details.json`

Generated by a new `scripts/generate-site-details.js` (same pattern as the existing `generate-alerts.js`), keyed by site name. Circuit/tunnel `status` values are seeded from each site's real gateway status in `network-data.json`, so the new data never contradicts an existing alert (e.g. TOK-Sales' existing VPN-outage alert lines up with a tunnel marked down, not against it).

Per site:

- **`circuits`**: one entry per gateway device at the site — `{ deviceId, isp, tier, connectionType, status, throughputUpMbps, throughputDownMbps, latencyMs, lossPct, latencyTrend, lossTrend, throughputTrend }`. Trend fields are `{ labels: [...24 hourly labels], data: [...] }`, matching the shape already used in `gateway-defaults.json`'s `uplinkHealth`/`throughput`.
- **`vpnTunnels`**: 2–4 entries per site — `{ id, peerName, vendor, status, latencyMs, jitterMs, lossPct, bandwidthUpMbps, bandwidthDownMbps, latencyTrend }`. `jitterMs`/`lossPct` are omitted when `vendor: 'mist'` (per the catalog's VENDOR-PARTIAL note — Mist has no per-tunnel jitter/loss field).
- **`hardware`**: `{ psuTotal, psuFailedDeviceIds: [...] }` — rollup used for both the health-badge count and naming specific devices in the Needs Attention panel.
- **`bgpFlaps`**: 0–3 events — `{ neighbor, previousState, currentState, timeAgo }`. Empty on most sites; populated on 1–2 sites that already have WAN-instability alerts, for narrative consistency.
- **`security`**: 0–2 rogue-AP detections — `{ ssid, bssid, band, rssi, classification, detectedAt }`.
- **`vlans`**: fixed 4-VLAN inventory (Corp/Secure/Guest/Prod, matching the names already used in `gateway-defaults.json`'s `throughputByVlan`) — `{ id, name, purpose, clientCount, bandwidthMbps }` per site.
- **`topApplications`**: `{ labels: [...], data: [...pct], colors: [...] }` — same shape as `gateway-defaults.json`'s `topApps`, for a doughnut chart.

## 4. Tab Contents

### Stage A — vital signs

- **Health badge**: uplink status/throughput/loss (with sparklines), VPN status summary ("3/3 up"), switch/AP health rollup, PSU rollup, routing-redundancy indicator ("2/2 paths available", derived client-side from uplink+tunnel status — no data of its own).
- **Needs Attention panel**: device issues (warning/critical/offline, by name) + PSU failures (by device name). Empty/collapsed when healthy.
- **WAN/Uplink section**: per-circuit identity + current throughput/latency/loss with sparklines.
- **LAN/Switching section**: per-switch status + PSU status detail (the drill-down behind the badge rollup).
- **Device inventory table**: one row per device, status/uptime, links to that device's existing page.
- **Alert feed**: filtered `alerts.json` view for this site.

### Stage A+B — adds

- **WAN/Uplink section**: cellular status + signal strength appended per circuit (Meraki: numeric signal; Mist: status only, no fabricated number).
- **VPN Tunnels section** (new): per-tunnel latency/jitter/loss/bandwidth table, jitter/loss blank for Mist tunnels.
- **BGP Flap Detector**: count + last-flap detail, feeding into the Needs Attention panel (e.g. "BGP flap detected 12m ago: HQ-Primary").
- **Wireless section** (new): AP health (carried from Stage A) + active client count with sparkline.

### Stage A+B+C — adds

- **Application Visibility section** (new): Top Applications doughnut chart.
- **VLAN/Segmentation section** (new): VLAN inventory table + per-VLAN client count + per-VLAN bandwidth. DHCP pool utilization stays excluded — matches the catalog's "not staged, blocked" call.
- **Wireless section**: Time-to-Connect breakdown appended (Assoc/Auth/DHCP/DNS stacked bar, same shape as the existing Frustration Leaderboard).
- **Security Intelligence widget** (new): rogue-AP detections, feeding the Needs Attention panel.

## 5. Explicit Scope Cuts

- **No click-to-expand trend overlays.** Every widget's sparkline is inline and fixed-window; there's no modal/detail-chart drill-down like the other 3 pages have. Can be added in a later round.
- **DHCP pool utilization**: excluded, per the widget catalog's "Not staged — blocked" determination (no viable bulk data path on either vendor today).
- **Fan/PSU**: PSU-only, no fan status — matches the catalog (fan dropped on both vendors).
- **Meraki's 4-value device-status enum** (online/alerting/offline/dormant) is not introduced as a separate vocabulary — this page reuses the app's existing online/warning/critical/offline enum; "warning" carries the same meaning the catalog calls "alerting."
